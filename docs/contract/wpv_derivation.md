# Exact PV plane decomposition for deep direct tables, w = 15 … 21

Companion to RESULTS.md Part 2, conclusion 5 ("w=21 -> eh up to 2^21 (22 bits) -> the
split-byte PV decomposition and s32 partial-sum bounds must be re-derived before speed
claims"). This file is that re-derivation. **Every number below is asserted by
`wpv_ref.py`** (same directory), which also proves bit-equality of the schemes against
an arbitrary-precision direct integer PV over adversarial randomized rows:

```
/usr/bin/python3 paper_softmax/bigrun/wpv_ref.py     ->  WPV_REF PASS
```

Scope: the accumulation `A[c] = sum_j eh_j * v_{j,c}` and normalizer `l = sum_j eh_j`
of the attention engine (SPECIFICATION.md 6.2), with the Q15 weights of 6.2.7
generalized to the deep direct tables of the long-context campaign. The f32 epilogue is
unchanged. Existing files are not modified; nothing here alters the filed w=15 contract.

---

## 0. Setting: what the contract fixes before any decomposition

* Weights: `eh = tab_{n,w}[idx] >> shift`, `shift = d >> BHI` consumed only for
  `d < (w+1)*2^BHI`, so `shift` lies in `[0, w]`; window is `w+1` doublings. Tables are
  generated by `offline_table_lab.direct_table(n, w)`:
  `tab[k] = RN(2^w * 2^(-k/2^n))` (60-digit Decimal, round half up).
* Values: `v8` in `[-127, 127]` (s8; the quantizer never produces -128). `dh <= 128`.
* Accumulator model (int8 tensor-core hardware): matrix units take 8-bit operands and
  accumulate in s32; the mixed `u8 x s8 -> s32` form (IMMA / dp4a class) is the primary
  target; `s8 x s8`-only units are covered in section 5, Alt C. One s32 accumulator may
  see at most `T_acc` keys; longer rows sum exact s32 partials into s64 — the mechanism
  already claimed for w=15 (SPECIFICATION.md aspect 38).

**The 2^w top-entry edge.** `tab[0] = RN(2^w * 2^0) = 2^w` **exactly**, and every other
entry is `< 2^w` (verified per table). So

* `eh` ranges over `[0, 2^w]`, and the top value `2^w` **is attained** — at
  `(idx, shift) = (0, 0)`, i.e. whenever `d < 2^(BHI-n)`. It is the only value needing
  `w+1` bits; everything else fits in `w` bits.
* The edge is not rare-by-construction: a row with all-equal scores whose `m*G` is a
  multiple of `2^BHI` has `d = 0` — hence `eh = 2^w` — at **every** key. Any bound that
  special-cases the top entry as "one key per row" is wrong; the derivation below never
  assumes sparsity of the edge (verified: an all-keys `eh = 2^w` row is part of the
  test suite).

## 1. Plane split of eh (recommended: radix-256 byte planes)

Write `eh` in base 256 with `P = ceil((w+1)/8)` digits ("planes"):

```
p_i  = (eh >> 8i) & 255          for i = 0 .. P-2      (full u8 digits)
p_top = eh >> 8(P-1)                                   (top digit, unmasked)
eh   = sum_i p_i * 2^(8i)                              (exact, for every eh in [0, 2^w])
```

The identity and all digit ranges are verified for **every** integer `eh` in
`[0, 2^w]` (not merely table-reachable values), so the split is valid for any table of
the `(n, w)` family with entries `<= 2^w`, any n.

| w  | eh_max          | P | plane widths and ranges                          | top-entry digits        |
|----|-----------------|---|--------------------------------------------------|-------------------------|
| 15 | 2^15 = 32,768   | 2 | p0: 8b [0,255];  p1: 8b [0,**128**]              | (0, 128)                |
| 16 | 2^16 = 65,536   | 3 | p0,p1: 8b [0,255];  p2: **1b {0,1}**             | (0, 0, 1)               |
| 17 | 2^17 = 131,072  | 3 | p0,p1: 8b [0,255];  p2: 2b [0,2]                 | (0, 0, 2)               |
| 18 | 2^18 = 262,144  | 3 | p0,p1: 8b [0,255];  p2: 3b [0,4]                 | (0, 0, 4)               |
| 19 | 2^19 = 524,288  | 3 | p0,p1: 8b [0,255];  p2: 4b [0,8]                 | (0, 0, 8)               |
| 20 | 2^20 = 1,048,576| 3 | p0,p1: 8b [0,255];  p2: 5b [0,16]                | (0, 0, 16)              |
| 21 | 2^21 = 2,097,152| 3 | p0,p1: 8b [0,255];  p2: 6b [0,32]                | (0, 0, 32)              |

How the edge is handled: the single `(w+1)`-bit value `2^w` has base-256 digits
`(0, …, 0, 2^(w-8(P-1)))`, and the top plane's container range is defined to include
that value. No datapath special case exists. For w = 15 this reproduces the filed
6.2.7 exactly (`eh_hi` in `[0, 128]`, `eh_lo` in `[0, 255]`).

**Two planes are possible only at w = 15 — honest statement.** Two u8 digits at radix
256 cover exactly `[0, 255*256 + 255] = [0, 65535]`; a radix > 256 leaves gaps
(digits stop at 255) and a radix < 256 covers less, so 16 bits is a hard ceiling for
two 8-bit planes. Hence:

* w = 16 misses by exactly one value (`2^16 = 65,536 > 65,535`). Three formal planes
  are required, but the third is the **1-bit carry** `p2 = [eh = 2^16]`, nonzero only
  at `(idx, shift) = (0, 0)` (verified). A kernel folds it as a predicated column-add
  of the value rows (`A2[c] += sum of v_{j,c} over carry keys`) — **no third matrix
  pass**; its worst case (all keys carrying) is still exactly accumulated, bound below.
* w >= 17 needs `w` bits even excluding the top value (`2^w - 1` is a w-bit number,
  w >= 17 > 16), so three genuine planes are unavoidable; no special-casing of the
  edge buys the plane back.

**Top-plane support (structural sparsity, verified per table).** `p2 != 0` requires
`eh >= 2^16`, i.e. `tab[idx] >> shift >= 2^16`. Since `tab[idx] <= 2^w`, this forces
`shift <= w-16`, i.e. `d < (w-15) * 2^BHI` — the key's score within `w-15` doublings
of the aligned row max. Verified exactly: for `shift <= w-17` **every** idx has
`p2 != 0`; at `shift = w-16` only `idx = 0` (the top entry); for `shift >= w-15`
plane 2 is identically zero. A kernel therefore skips the plane-2 matrix pass for any
key tile entirely below `w-15` doublings — for typical attention rows that is all but
a handful of tiles. (The p1 plane admits no such rule: full u8 range throughout the
window.)

The split is applied **after** the shift (`eh = tab[idx] >> shift`, then digits);
byte-slicing table entries before the shift does not commute with it.

## 2. Per-plane worst-case accumulation and the s32 bound

One s32 accumulator sums `T` products `p_i,j * v_j` with `|v_j| <= 127` and
`0 <= p_i,j <= pmax`. Worst-case magnitude is `pmax * 127 * T` (all products at the
rail, same sign), and because all addends then share one sign, every partial sum in
**any** association is bounded by the total. Exactness condition:

```
pmax * 127 * T  <=  2^31 - 1  =  2,147,483,647          =>   T_acc = floor((2^31-1) / (pmax*127))
```

(The negative rail `-pmax*127*T >= -2^31` is one unit roomier; the symmetric bound is
used.) All eight plane magnitude classes that occur, with the arithmetic shown and the
tightness demonstrated by a real s32-container dot product of exactly `T_acc` keys in
`wpv_ref.py`:

| pmax | per-key = pmax*127 | T_acc (max T) | product at T_acc      | margin to 2^31-1 | product at T_acc + 1 (overflows) |
|------|--------------------|---------------|-----------------------|------------------|----------------------------------|
| 255  | 32,385             | **66,311**    | 2,147,481,735         | 1,912            | 2,147,514,120                    |
| 128  | 16,256             | **132,104**   | 2,147,482,624         | 1,023            | 2,147,498,880                    |
| 32   | 4,064              | 528,416       | 2,147,482,624         | 1,023            | 2,147,486,688                    |
| 16   | 2,032              | 1,056,832     | 2,147,482,624         | 1,023            | 2,147,484,656                    |
| 8    | 1,016              | 2,113,665     | 2,147,483,640         | 7                | 2,147,484,656                    |
| 4    | 508                | 4,227,330     | 2,147,483,640         | 7                | 2,147,484,148                    |
| 2    | 254                | 8,454,660     | 2,147,483,640         | 7                | 2,147,483,894                    |
| 1    | 127                | 16,909,320    | 2,147,483,640         | 7                | 2,147,483,767                    |

Note on the filed numbers: Table 1 of the specification states `A_lo` exact for
`T <= 66,311` (identical to the derivation here) and `A_hi` exact for `T <= 131,072`;
the exact maximum for the 128-plane is **132,104** (`132,104 * 16,256 = 2,147,482,624
<= 2^31 - 1 < 132,105 * 16,256`), so the filed `2^17` is a valid conservative round
number, not the supremum.

**The binding constraint is 66,311 for every w.** Each scheme contains a full-range
u8 plane (p0; also p1 for w >= 16), and the top plane's own limit (528,416 even at
w = 21) is far looser. Consequences:

* The per-s32-accumulator tile bound of the filed w=15 kernel design **carries over
  unchanged to every deep table**: deeper tables do not tighten the tile bound; they
  add one (mostly skippable) plane and widen the recombination and the normalizer.
* Beyond 66,311 keys, exact s32 partials over at most 66,311 keys each are summed in
  s64 — the aspect-38 mechanism, unchanged. At `T = 1,000,000`: `ceil(10^6 / 66,311)
  = 16` partial groups per plane. With FlashAttention-style 128-key tiles, an s32
  accumulator must spill to s64 every `floor(66,311 / 128) = 518` tiles
  (`518 * 128 = 66,304 <= 66,311 < 519 * 128`); real kernels spill far more often
  anyway (per k-tile), so the bound costs nothing in practice.
* At `T = 10^6` and w = 21 even the top plane (528,416) must be partialed — no plane
  is "safe to run to a million" in s32.

Worst case constructed from the real tables (not just container arithmetic): every
n=13 table contains entries with low byte 255 (e.g. w=21: `tab[26] = 2,092,543`);
scores hitting such an entry at shift 0 on every key give a p0 plane that reaches
`255 * 127 * 66,311 = 2,147,481,735` in a genuine int32 accumulation — 1,912 below
INT32_MAX — and one more key would overflow (`2,147,514,120 > 2^31 - 1`, refuted
arithmetically, not by wrapping numpy). `wpv_ref.py` runs exactly this, per w, plus a
70,001-key version crossing the tile boundary.

## 3. Exact recombination in s64

```
P = 2:   A = A1 * 256 + A0
P = 3:   A = A2 * 65,536 + A1 * 256 + A0        (each A_i signed: v is signed)
```

Multiplication, not a language-level shift — `A_i` may be negative (6.0.2 carries
over). Bounds, in two layers:

* **Value bound (joint).** Because `sum_i p_i * 2^(8i) = eh` exactly,
  `A = sum_j eh_j * v_j` and `|A| <= 127 * T * 2^w`.
* **Intermediate bound (evaluation order).** Evaluating the recombination
  left-to-right, the worst partial magnitude coefficient is
  `C_w = 2^w + 2^(8(P-1)) - 1` (per-plane rails are not jointly attainable, but the
  intermediate `A2*65,536 + A1*256` can exceed the joint rail transiently). Every
  intermediate is exact in s64 iff `127 * C_w * T <= 2^63 - 1`:

| w  | C_w       | T_rec = floor((2^63-1)/(127*C_w)) |
|----|-----------|------------------------------------|
| 15 | 33,023    | 2,199,224,076,193                  |
| 16 | 131,071   | 554,088,827,186                    |
| 17 | 196,607   | 369,391,612,038                    |
| 18 | 327,679   | 221,634,516,304                    |
| 19 | 589,823   | 123,130,119,829                    |
| 20 | 1,114,111 | 65,186,482,018                     |
| 21 | 2,162,687 | 33,580,900,365                     |

Never binding: >= 3.3 * 10^10 keys for every w — 33,580 times the 1M campaign length
at w = 21. Resulting `|A| <= 127 * T * 2^w = 266,338,304 * 10^6 < 2^48` at `T = 10^6`, w = 21; the two
f32 conversions and the division of the epilogue are unchanged in domain (a nonzero
`eh_j / l >= 1 / (T * 2^w) >= 2^-41` at `T <= 2^20`, w = 21, so no subnormal can
arise, as in 6.0.4).

## 4. The normalizer l

`l = sum_j eh_j <= T * 2^w`, with the rail attained by the all-`d=0` row. Exactness:

```
s64:  T <= floor((2^63-1) / 2^w) = 2^(63-w) - 1
s32:  T <= floor((2^31-1) / 2^w) = 2^(31-w) - 1
```

| w  | l in s32 exact iff T <= | l in s64 exact iff T <=  |
|----|--------------------------|--------------------------|
| 15 | 65,535  (as filed)       | 281,474,976,710,655      |
| 16 | 32,767                   | 140,737,488,355,327      |
| 17 | 16,383                   | 70,368,744,177,663       |
| 18 | 8,191                    | 35,184,372,088,831       |
| 19 | 4,095                    | 17,592,186,044,415       |
| 20 | 2,047                    | 8,796,093,022,207        |
| 21 | 1,023                    | 4,398,046,511,103        |

At depth an s32 normalizer is useless (1,023 keys at w=21): `l` is an s64 reduction
(cheap — one column, not dh). If the kernel already forms per-plane column sums, `l`
falls out exactly as `l = sum_i 2^(8i) * colsum(p_i)` (this identity is how
`wpv_ref.py` computes it, verified bit-equal against the direct sum).

## 5. Recommended scheme per w, and alternatives

**Recommended (u8 x s8 -> s32 units).** Byte planes of section 1; per-plane s32
accumulators over tiles of at most 66,311 keys; s32 partials summed in s64; s64
recombination; s64 normalizer.

| w  | eh_max    | planes (pmax)   | matrix passes per k-tile           | T_acc | T_rec s64          | l s32 iff T <= | table bytes (n=13) |
|----|-----------|-----------------|-------------------------------------|-------|--------------------|----------------|--------------------|
| 15 | 32,768    | 255, 128        | 2                                   | 66,311| 2,199,224,076,193  | 65,535         | 16,384 (u16)       |
| 16 | 65,536    | 255, 255, 1     | 2 + predicated carry-add            | 66,311| 554,088,827,186    | 32,767         | 32,768 (u32) *     |
| 17 | 131,072   | 255, 255, 2     | 3; skip pass 3 when tile d >= 2*2^BHI | 66,311| 369,391,612,038  | 16,383         | 32,768 (u32)       |
| 18 | 262,144   | 255, 255, 4     | 3; skip pass 3 when tile d >= 3*2^BHI | 66,311| 221,634,516,304  | 8,191          | 32,768 (u32)       |
| 19 | 524,288   | 255, 255, 8     | 3; skip pass 3 when tile d >= 4*2^BHI | 66,311| 123,130,119,829  | 4,095          | 32,768 (u32)       |
| 20 | 1,048,576 | 255, 255, 16    | 3; skip pass 3 when tile d >= 5*2^BHI | 66,311| 65,186,482,018   | 2,047          | 32,768 (u32)       |
| 21 | 2,097,152 | 255, 255, 32    | 3; skip pass 3 when tile d >= 6*2^BHI | 66,311| 33,580,900,365   | 1,023          | 32,768 (u32)       |

(* w=16 alternative storage: 16,384 B, see section 6. Skip rule: plane 2 is
identically zero when every key in the tile has `shift >= w-15`, section 1.)

**Alt A — single-pass s64 (architectures with fast 32 -> 64 accumulate, or scalar/
SIMD integer cores).** Products `eh * v` fit s32 for every w
(`2^21 * 127 = 266,338,304 < 2^31`); accumulate the s32 products into s64 directly —
no planes, no recombination. Exact iff `127 * T * 2^w <= 2^63 - 1`:
T <= 2,216,338,399,296 (w=15) down to **34,630,287,489** (w=21). Unbounded in
practice.

**Alt B — binary64 accumulation (the filed 6.2.7 alternative, array frameworks).**
Exact while every partial sum's magnitude stays <= 2^53: `127 * T * 2^w <= 2^53`,
i.e. T <= 2,164,392,968 (w=15), 1,082,196,484 (w=16), 541,098,242 (17),
270,549,121 (18), 135,274,560 (19), 67,637,280 (20), **33,818,640 (w=21)** — still
33.8x the 1M campaign length. The existing f64 reference path survives all deep
tables unmodified.

**Alt C — 7-bit planes for s8 x s8-only units** (the "three planes of at most 7 bits"
route of 6.2.7, generalized). `P7 = ceil((w+1)/7)` radix-128 digits, every digit in
`[0, 127]` hence s8-safe with no unsigned recode:

| w        | P7 | plane pmax          | binding T_acc |
|----------|----|---------------------|---------------|
| 15       | 3  | 127, 127, 2         | 133,144       |
| 16       | 3  | 127, 127, 4         | 133,144       |
| 17       | 3  | 127, 127, 8         | 133,144       |
| 18       | 3  | 127, 127, 16        | 133,144       |
| 19       | 3  | 127, 127, 32        | 133,144       |
| 20       | 3  | 127, 127, 64        | 133,144       |
| 21       | 4  | 127, 127, 127, 1    | 133,144       |

Binding plane: `127 * 127 * 133,144 = 2,147,479,576 <= 2^31 - 1 < 127 * 127 *
133,145`. w = 21 is the one width needing a fourth plane — and that plane is the
1-bit carry `[eh = 2^21]`, foldable as a predicated add exactly like w=16's byte
carry (top-plane T_acc alone: 16,909,320). For w <= 20 three 7-bit planes suffice
(top digit <= 64 <= 127). The filed recode-u8-as-s8 trick (subtract 128 from a byte
plane, add `128 * colsum(v)` back) remains available per byte plane as a 2-passes-
per-byte-plane alternative on such units; it is exact but adds the column-sum
correction per accumulator tile.

**Alt D — 16-bit-multiplier units (e.g. s16 dot-product paths).** Two digits at
radix 2^11 cover every w <= 21: `lo = eh & 2047`, `hi = eh >> 11 <= 2^(w-11)`
(= 1,024 at w=21; both digits s16-safe). Binding: lo plane,
`2047 * 127 * T <= 2^31 - 1  =>  T <= 8,260` per s32 accumulator (hi plane at w=21:
16,513). Two passes, but short tiles.

**No clean 2-plane scheme exists for w >= 16 on 8-bit units** (section 1); the
recommendation above is the minimum: 2 matrix passes (w=15), effectively 2 (w=16,
carry folded), 3 with a structurally skippable third (w=17..21).

## 6. Shared-memory cost of the table

Entries `2^n`; the campaign uses n = 13 (RESULTS.md Part 2: tau is n-independent for
n = 13/14/15, window depth w is the only knob). Storage width is set by the largest
entry `2^w`:

| w  | entry width needed        | n=13 bytes           | notes                                          |
|----|---------------------------|----------------------|------------------------------------------------|
| 15 | 16b (max 32,768 fits u16) | 8,192 x 2 = 16,384   | filed layout                                   |
| 16 | 17b — **one** entry > u16 | 8,192 x 4 = 32,768   | or u16 16,384 B + idx-0 fix (below)            |
| 17 | 17b — **all 8,192** > u16 | 8,192 x 4 = 32,768   | min entry 65,542 > 65,535 (verified)           |
| 18 | 18b — all > u16           | 8,192 x 4 = 32,768   |                                                |
| 19 | 19b — all > u16           | 8,192 x 4 = 32,768   |                                                |
| 20 | 20b — all > u16           | 8,192 x 4 = 32,768   |                                                |
| 21 | 21b — all > u16           | 8,192 x 4 = 32,768   |                                                |

w >= 17 entries exceed u16 not just at the top: the smallest entry is
`RN(2^w * 2^(-8191/8192)) ~ 2^(w-1)` which already exceeds 65,535 from w = 17 on. So
u32 (or packed u24: 8,192 x 3 = 24,576 B, at the cost of unaligned loads) is required.

**w=16 u16 trick (verified exact):** store entry 0 as 0 in a u16 table and evaluate
`eh = (tab16[idx] >> shift) + ((idx == 0) ? (2^16 >> shift) : 0)`. Only entry 0
(= 65,536) exceeds u16; the fix reconstructs `2^(16-shift)` exactly for every shift
in `[0, 16]`. Keeps the table at 16,384 B.

For scale (vendor datasheet context, not part of the derivation): 32,768 B against
164 KiB (A100) / 228 KiB (H100) of shared memory per SM — 2x the filed w=15 table,
still a small fraction of an SM, but per-CTA replication should be weighed at high
occupancy; the u24/u16-fix options above exist if it ever binds.
